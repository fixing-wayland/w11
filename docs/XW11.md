# xw11 — the X11 proxy

`xw11` is an X11 display. It binds a display number of its own, forwards every byte to
the session's real X server — Xwayland, on a Wayland session — and answers the handful of
requests that server has no answer for, because the windows they are about are native
Wayland toplevels that were never X windows at all.

That is the whole idea. The other six tools in this tree are clones: they speak the
originals' command lines and print the originals' bytes, and a script that calls
`xdotool` has to be pointed at `wdotool` (or have it symlinked over the original) before
any of it helps. `xw11` is the other direction. Point **the real `xdotool`** at
`DISPLAY=:20` and it lists your `foot` window, activates it, moves it, types into it and
reads its properties — unmodified, from the distribution, with none of our code in the
process. So does the real `wmctrl`, the real `xprop`, the real `xrandr`, python-xlib,
`xdpyinfo`, AutoKey, a status bar, and whatever else in the thirty-year X11 tail you
already have. [AGENTS.md](../AGENTS.md) says that if X supports it we support it; this is
route 5 of its ladder, an X11 protocol proxy, and it is the widest one in the tree.

What it costs is written down: the **[What differs](#what-differs)** table at the end of
this document is one row per thing X does that `xw11` does not do yet, each with the route
that would close it and what that route costs.

> Everything measured below was measured on a headless sway 1.11 with Xwayland 24.1.10, or
> against Xvfb 21.1.22, on 2026-09-10 and 2026-09-11, unless the sentence says where else.

## How it starts

Nothing has to be started by hand. On a Wayland session `xdotool`, `wmctrl`, `xprop` and
`xrandr` — the symlinks this project installs over the originals, see
[Installing over the originals](../README.md#installing-over-the-originals) — run the
**original** program against `xw11`'s display, and the first call that needs a proxy starts
one. [The wrapper rules](#the-wrapper-rules) below are the six steps that decide it.

The proxy is spawned the way `wdotool`'s input daemon is, and for the same reasons: fork,
`setsid`, fork, stdio to the log, every inherited descriptor closed, out of the launcher's
systemd scope, cwd `/`, re-exec as `xw11 __serve`. The wrapper then polls for the display
file for two seconds at 50 ms. Measured on this box on 2026-09-11, six runs: **53, 105,
104, 105, 109 and 203 ms** from the fork to a display file a client can dial — one to four
polls, so they cluster on multiples of the interval, and **105 ms** is the number to quote.
That is by the `python3 -m xw11` route, the slow one; an installed console script skips the
`PYTHONPATH` walk. The two seconds are for a loaded machine, not for the ordinary case.

Ten wrappers starting at once leave exactly one `__serve`. The session lock is an abstract
socket bind, so a starter killed between the bind and the display file leaves nothing
behind to recognise, and the nine losers exit as soon as the winner's display file appears.

**As root.** `ssh root@box wmctrl -l`, `sudo xdotool key a` and a root cron line reach the
seated user's proxy, and start none of their own. Root has no session of its own to proxy:
pam_systemd hands an `ssh root@` login its own `/run/user/0`, which is empty, and with
`$XDG_RUNTIME_DIR` unset the lookup used to answer `/tmp/wdotool-0` — so the display file the
desktop's proxy writes was never found and a second proxy would have been started in root's
runtime directory, with no `$WAYLAND_DISPLAY` to connect to and nothing in the session able to
reach it. The wrapper now asks `passthrough.session_uid()` — logind, not `SUDO_UID`, which an
`ssh root@` login has not got — and looks in **that** user's runtime directory for the display
file and in their `$XAUTHORITY` for the cookie. Attach or nothing: where that session has no
proxy running, root does not start one, the clone runs, and one line under `XW11_DEBUG` says
which uid was looked at. Measured on a headless sway on 2026-09-11: the seated user's
`xw11 --print-display` answered `:20`, and a second process with `XDG_RUNTIME_DIR` unset,
`os.getuid()`/`os.geteuid()` answering 0 and `session_uid()` answering the seated uid got the
same `:20` and spawned nothing; with the uid left unknown the same process found no display
file and would have spawned.

### By hand

| command | what it does |
|---|---|
| `xw11` | starts the proxy in the background and prints its `:N` |
| `xw11 --print-display` | the `:N` of the running proxy, starting one if there is none: `DISPLAY=$(xw11 --print-display) python3 my-xlib-script.py` |
| `xw11 --foreground` | serves in this process instead of daemonising (rigs, tests, a user service) |
| `xw11 --passthrough` | forwards every byte and synthesizes nothing |
| `xw11 --display :N` | takes that number, or fails; there is no scan |
| `xw11 --upstream :M` | forwards to that X server instead of `$DISPLAY` |
| `xw11 --stop` | unlinks the display file and `SIGTERM`s the pid it names |
| `xw11 __serve` | the argv the daemonised child is re-exec'd with. A word no shell user types, and one `ps` can be grepped for — `wdotool __daemon`'s precedent |

`xw11 --stop` and `xw11 --foreground` still act on the **calling** user's runtime directory, so
root stops root's proxy and not the session's. **Not yet**, and deliberately small: no ladder
rung is needed here — this is work in our own tree, not a route out to a protocol or a bus. The
`uid=` parameter `xw11/display.py:display_file_path()` and `w11common/session.py:runtime_dir()`
now take is threaded into `xw11/cli.py`'s own three lookups (`stop()`, `serve()`'s second-proxy
refusal and the session lock) the way `xw11/wrap.py` already threads it. Cost: one parameter per
call site plus the owner's decision — whether `sudo xw11 --stop` should be able to stop a proxy
the seated user's session owns.
`--print-display` is already right: it goes through `ensure_proxy()`.

`--passthrough`, `--upstream` and `--display` describe the proxy that will be **started**,
so they are carried into the daemonised child's own argv: `ps` then shows
`xw11 __serve --passthrough`. When a proxy is already running, a command carrying one of
the three is refused rather than answered with the one that is there — a session has one
proxy — and the refusal names the two ways out: `xw11 --stop`, or `--foreground`.

A proxy given a display number takes **no session lock** and does not overwrite a live
proxy's display file. That is what lets `W11_PARITY_PROXY=1 sh scripts/parity-oracle.sh`
run its own proxy on `:98` beside a session one.

With no `--upstream` the proxy takes `$DISPLAY`, and with no `$DISPLAY` either it finds the
session's own X server (`session.find_x_display()`). That is what makes `sudo xdotool key a`
and a cron line work: the wrapper that spawned the proxy had no `DISPLAY` to pass on.

### As a session service

The NixOS module carries `programs.w11.proxy.enable`: start `xw11 --foreground` with the
graphical session, as a systemd user service, instead of letting the first X tool start it
on demand. Off unless you ask for it — nothing needs it. Turn it on for the one thing
on-demand cannot give you: **shadow window ids that are stable for the whole session**. A
proxy started on demand exits fifteen minutes after its last client (`_IDLE_SECONDS = 900.0`,
checked every `_CHECK_SECONDS = 15.0`), and the ids it minted mean nothing to the next one,
so a script that saves an id, sleeps an hour and acts on it wants a proxy that never idles.
The cost is one process and one Xwayland pinned for the session.

The unit waits for the session's X server rather than giving up on it: `Restart=on-failure`,
`RestartSec=5`, and `startLimitIntervalSec = 0` so there is no start limit. The proxy
refuses to start when nothing answers `$DISPLAY` and no Xwayland is running, and on GNOME
and KWin — both start Xwayland on demand — that is the ordinary state when
`graphical-session.target` is reached. With systemd's default rate limit, five starts in
ten seconds, the unit would be `failed` before the session's first X tool ever ran.

### The display, the sockets and the cookie

The proxy binds **both** of a display's sockets, the abstract name first, because libxcb
tries the abstract name first: a proxy that owns only the filesystem path is silently
bypassed by whatever holds the abstract name (measured against libxcb 1.17.0 on 2026-09-10).
`DISPLAY` is always spelled `:N`; `unix:N` is refused outright by libxcb 1.17.

Only a **socket** at `/tmp/.X11-unix/XN` is treated as a possible corpse and probed with
`connect()`. A regular file, a directory or a symlink there means the number is somebody
else's and the scan moves on: `xw11` unlinks exactly what it created.

Authentication is one appended `.Xauthority` record for the proxy's own number, written
into the file the upstream cookie came from, because the X server re-reads its `-auth` file
and matches on (protocol name, cookie bytes) while ignoring the display recorded in the
client's entry. It is removed at exit. Where there is no cookie at all — sway starts
Xwayland with no `-auth` — nothing is written and the empty setup is forwarded, which is
what was measured to work there. A cookie that exists and cannot be appended to (a
read-only `.Xauthority`, an `$XAUTHORITY` belonging to another uid after a `sudo`) is a log
line and not a refusal: the proxy serves, and a client whose cookie the upstream then
refuses gets the upstream's own `Failed` reason.

The cookie root reads is the seated user's, for the same reason `as root` looks in the seated
user's runtime directory: `/root/.Xauthority` authorises nothing on the session's Xwayland. The
lookup is `passthrough.find_xauthority(e, uid)`, the one the clones already use — `$XAUTHORITY`
when it names a file that exists, then Mutter's `.mutter-Xwaylandauth.*`, GDM's `xauth_*` and
`gdm/Xauthority` in that uid's runtime directory, then their `~/.Xauthority` — and it is
preferred over this process's own files rather than replacing them, so a caller inside a session
reads exactly the files it read before.

One proxy per session owns `$XDG_RUNTIME_DIR/xw11/display`. A second proxy serves normally
and does not write that file, because overwriting it and then unlinking it at its own exit
would take the live proxy down with it through the file-gone check. The log line says so.

The proxy's own `DISPLAY` and `XAUTHORITY` are the **upstream's**: a backend that reads the
X plane itself must reach Xwayland, never the loop it is running inside.

### Two refusals before it allocates

Neither is a policy; each names the route that would close it and what it costs.

* **Its own display as upstream** (`XW11_DISPLAY` or `--display` equal to `--upstream` or
  `$DISPLAY`): every request would be forwarded to this process's own loop, which is waiting
  to write the answer. Pick another number, or point `--upstream` at the session's real X
  server.
* **No X server to forward to** (nothing answers the upstream and no Xwayland is running):
  `xw11` forwards to the session's X server and does not start one — **not yet**. The route
  is asking the compositor for it (AGENTS.md route 2: sway's `exec Xwayland`, Mutter's and
  KWin's own on-demand start), at the cost of owning the lifetime of a server the compositor
  believes is its own. `Xwayland :N &`, or `--upstream` on a live display, is the way through
  today.

## The request policy

Every request belongs to one of five classes.

| class | what happens | what upstream gets |
|---|---|---|
| **PASS** | forwarded byte for byte; the reply, if any, streams back untouched | the request |
| **EDIT** | forwarded; the reply is rewritten on the way back. A length change rewrites the reply's length word and the sequence never moves; an error for that sequence passes untouched and drops the editor | the request |
| **CONSUME** | the request produces nothing for the client | `NoOperation` (opcode 127) in its place, so the sequence delta stays zero |
| **ANSWER** | the proxy synthesizes the reply, or a 32-byte error, at dispatch time | `GetInputFocus` (opcode 43); its 32-byte reply comes back in stream order carrying the substituted sequence, and the proxy writes the stored packet in its place |
| **BATCH** | a RandR write inside a grab: ANSWER or CONSUME with a deferred side effect | as above |

**Why the placeholder.** libxcb sets `request_completed = request_read - 1` on *any* packet
it reads, so a locally written reply for request N+1 that goes out before the forwarded
reply for N arrives makes the client read `NULL` for N. The proxy cannot know whether a
forwarded reply is outstanding without an opcode-has-reply table it does not keep; the
`GetInputFocus` placeholder gives exact ordering with no table, no timer and 32 bytes of
state. It costs one round trip per locally answered reply-bearing request — about 70 µs,
under 2 ms for a whole `xdotool search`.

Where a policy says "shadow", the window field is an id the registry minted; "root" is the
setup's root; everything else is real and passes. **An unknown id — a dead shadow
included — passes, and upstream answers `BadWindow` itself**, with the serial the tools
print.

### Extensions

No extension major number is written down anywhere in `xw11`. They are per server: RANDR is
139 on Xwayland and 140 on Xvfb 21.1.22, XTEST 132 on both. The proxy asks
`QueryExtension` on its own connection and resolves whatever comes back.

| extension | request | policy |
|---|---|---|
| BIG-REQUESTS | Enable | PASS, and the framing switches with it |
| XKEYBOARD | UseExtension, GetMap, GetNames, GetState, LatchLockState, SelectEvents | PASS |
| XInputExtension, Generic Event Extension | everything | PASS |
| XINERAMA | IsActive, QueryScreens | PASS — Xwayland's Xinerama is already the compositor's output list |
| XTEST | GetVersion, CompareCursor | PASS |
| XTEST | FakeInput | CONSUME → the input daemon; with no daemon route, PASS |
| XTEST | GrabControl | CONSUME |
| RANDR | every read minor | PASS |
| RANDR | SetCrtcConfig, SetScreenSize, SetCrtcTransform | BATCH |
| RANDR | SetOutputPrimary | PASS **and** recorded into the batch |
| RANDR | SetScreenConfig | ANSWER: a batch of one |
| RANDR | CreateMode, DestroyMode, AddOutputMode, DeleteOutputMode, SetCrtcGamma, SetPanning, SetMonitor, DeleteMonitor, ChangeOutputProperty | PASS |

Errors the proxy synthesizes carry `major` = the request's opcode byte, `minor` = its minor
byte and `bad` = the offending id, in the same layout a live server writes, so Xlib's
default handler prints the same five lines it prints for a server error.

### A refusal is silence on the wire and one line in the log

X gives a client **no error** when a redirecting window manager ignores its
`ConfigureWindow`, `MapWindow` or focus request: the request is void and the window manager
did what it wanted. A backend refusal on a CONSUMEd request is therefore silence on the
wire and one line in the proxy log carrying the compositor's own sentence. Measured on this
rig with a tiled `foot`:

```console
$ xdotool windowmove <shadow> 70 70 ; echo rc=$?
rc=0
$ tail -1 /tmp/xw11-1000.log
... the sway backend refused move_window(94..., 70, 70) (sway: cannot move a tiled window
    to an absolute position (floating enable it first)): the request is silence on the
    wire, as X is when a window manager ignores one, and this line is the diagnostic
```

`wdotool windowmove` on the same window prints that sentence on stderr and exits 1. The
difference is not a choice about what *should* happen; it is what X does. Inventing a
`BadWindow` there would be bytes no X server ever sent. This is the trade the whole proxy
makes — diagnostics move from stderr to the log — and `XW11_DEBUG=1` is where the rest of
them are.

The same rule covers a state the compositor has no word for. `wmctrl -r WXL-Foot -b
add,maximized_vert` on sway exits 0, prints nothing, and the log carries the backend's own
sentence with its "not yet" and its rung. `add,fullscreen` on the same window and the same
rig does reach sway, so the gap is per state and not per command.

### SendEvent: the EWMH messages, and the dual-plane rule

An EWMH `ClientMessage` about a **real** X window can be done twice — once by Xwayland's own
window manager and once by the compositor, through the toplevel that X window is paired
with. The proxy picks one, and it picks with the X server's own answer:

> A routed message whose `type` atom is in **upstream's** `_NET_SUPPORTED` passes through
> untouched: the xwm handles it and the compositor must not do it again. One whose type
> upstream does not name is routed through the paired compositor handle and consumed.

with one clause the atom list cannot express. `WM_PROTOCOLS` and `WM_CHANGE_STATE` are
**ICCCM's**, not the EWMH's, and no `_NET_SUPPORTED` list on any compositor has ever named
either — the atom hint arrived with the EWMH and those two predate it. The xwm reads them on
its own dedicated path, so on a real X id they always pass. Asking the list about them would
answer "no" for ever, and the two things it would eat are a client's own `WM_DELETE_WINDOW`
and its `_NET_WM_PING` pong — the pong being what tells Mutter, KWin and wlroots that the
client is not hung.

wlroots' Xwayland root names **19** atoms and not one of them is a desktop atom: no
`_NET_WM_DESKTOP`, no `_NET_CURRENT_DESKTOP`, no `_NET_NUMBER_OF_DESKTOPS`, no
`_NET_MOVERESIZE_WINDOW`, no `_NET_FRAME_EXTENTS`, no `_NET_WM_WINDOW_TYPE`, no
`_NET_WM_PID`. So on this rig, for the **xterm**, which is a real X window:

| command | which plane does it |
|---|---|
| `wmctrl -a`, `wmctrl -c`, `xdotool windowactivate` | the xwm's: `_NET_ACTIVE_WINDOW` and `_NET_CLOSE_WINDOW` are in its list |
| `wmctrl -R` (its `_NET_WM_DESKTOP` half) | the compositor's, through the paired handle |
| `wmctrl -r -e` | the compositor's — and without the proxy `wmctrl` does not send that message at all: it reads `_NET_SUPPORTED` first, does not find `_NET_MOVERESIZE_WINDOW`, and falls back to a plain `ConfigureWindow` |
| `xdotool windowmove`, `windowsize`, `windowraise`, `windowfocus`, `windowmap`, `windowunmap`, `windowclose` | Xwayland's: they are core requests on a real window and the proxy never touches them |
| `xdotool windowminimize` | the xwm's: `WM_CHANGE_STATE` is ICCCM and never in any `_NET_SUPPORTED`. What sway then does with a minimize request for an X window is set a flag and nothing more; that is sway's gap, one verb wide, and routing it from here instead would be a second minimize on top of the compositor's own — measured, it moved the xterm from workspace 1 to `__i3_scratch`, where a direct run leaves it where it is |
| a polite closer's `WM_DELETE_WINDOW` | the xwm's: it carries the message to the X client, which is the only party that can save a file before it exits. A shadow has no X client, which is why the same message to a shadow is `backend.close` |

This is the rule `wwmctl` already follows for its own two planes. What a user sees: a
command on an X window behaves exactly as it did before the proxy existed, unless the X
server has no answer for it, and then it starts working.

The routing table itself, for a message whose window is a shadow or the root:

| type | window | route |
|---|---|---|
| `_NET_ACTIVE_WINDOW` | shadow | `backend.activate` |
| `_NET_CLOSE_WINDOW` | shadow | `backend.close` |
| `_NET_WM_STATE` | shadow | action and up to two atoms → `backend.set_state` |
| `_NET_WM_DESKTOP` | shadow | `backend.set_window_desktop`; `0xFFFFFFFF` → sticky |
| `_NET_MOVERESIZE_WINDOW` | shadow | the flag bits select x, y, w, h → `move_window` / `resize`; gravity ignored |
| `WM_CHANGE_STATE` | shadow | `3` → `backend.minimize` |
| `WM_PROTOCOLS` / `WM_DELETE_WINDOW` | shadow | `backend.close` |
| `_NET_CURRENT_DESKTOP` | root | `backend.set_desktop` |
| `_NET_NUMBER_OF_DESKTOPS` | root | `backend.set_num_desktops` |
| `_NET_SHOWING_DESKTOP` | root | **not yet**: forwarded to the X server and logged — see the table at the end |
| anything else | any | PASS |

## A shadow window

A native Wayland toplevel the compositor does not report an X id for gets a **shadow**: a
window id minted out of the range the X server allocated to the proxy's own connection,
`rid_base | n` with a 21-bit mask. On the rig that is `0x600001` for the first one.
Xwayland's own ids are `(client << 21) | serial` and the range is the server's promise, so
a shadow can never collide with a real Xwayland window, and an upstream error for one is
impossible.

A toplevel the compositor **does** report an X id for is real: it gets no shadow, and every
request naming it is forwarded to Xwayland. The proxy trusts the backend's `xid` and
repeats no matching. A pairing that settles late — a title that arrives after the window
did — destroys the shadow and the real id takes its place; the reverse never happens.

`ListProperties` answers:

```console
_NET_WM_PID(CARDINAL) = 1774386

_NET_WM_DESKTOP(CARDINAL) = 0
_NET_WM_STATE(ATOM) =
_NET_WM_WINDOW_TYPE(ATOM) = _NET_WM_WINDOW_TYPE_NORMAL
WM_STATE(WM_STATE):
                window state: Normal
                icon window: 0x0
_NET_FRAME_EXTENTS(CARDINAL) = 0, 0, 0, 0
WM_PROTOCOLS(ATOM): protocols  WM_DELETE_WINDOW
```

Eleven names, twelve with `WM_TRANSIENT_FOR` where the toplevel has a parent. `_NET_WM_PID`
is left out when the compositor does not know the pid, and `WM_CLIENT_MACHINE` when the
kernel will not say the hostname.

`_NET_WM_STATE` is empty above, and that is the sway answer rather than a bug: nine of the
eleven state bits are the rich ones that only a `views()` backend carries a field for,
`_NET_WM_STATE_FOCUSED` among them, and sway has no `views()` at all. The two that are not
— `_NET_WM_STATE_FULLSCREEN` and `_NET_WM_STATE_STICKY` — come off the tree node the
registry already walks for the xid pairing, exactly where `wxprop` reads them, so the same
foot after `swaymsg '[app_id=footw] fullscreen enable'` prints
`_NET_WM_STATE(ATOM) = _NET_WM_STATE_FULLSCREEN` through the proxy and through
`wxprop -id` alike.

`WM_STATE` is synthesized on **every** backend, not only the rich ones. The design's
original reason for that turned out to be wrong — `xdotool getwindowfocus` reads the
property and does *not* climb to the parent when it is absent, measured with the property
tombstoned out of a live shadow — but the property stays, for the readers that do care:
Mutter writes it on every X11 window it manages, so a shadow answers "is this minimized?"
the way its X twin does. This is the one row where the proxy's set is wider than `wxprop`'s,
which writes `WM_STATE` only on a `views()` backend.

`_NET_FRAME_EXTENTS` is four zeroes, and that is the true number: the rect every backend
reports is the whole toplevel and `GetGeometry` answers that same rect, so python-ewmh and
devilspie2 subtract it and get the right answer.

### Geometry, and `GetProperty` exactly

`GetGeometry` on a shadow answers the compositor's logical pixels. On sway that is one X
device pixel per compositor logical pixel even under `output HEADLESS-1 scale 2`, measured:
the tree rect, `xwininfo`'s Width/Height and `xdpyinfo`'s dimensions all read **640x360** at
scale 2 where they read 1280x720 at scale 1. Xwayland's screen shrinks with the logical
size, so a shadow's rect needs no scaling factor of its own.

`GetProperty` honours the request the way a server does, and every row below was measured
against Xvfb 21.1.22 from a raw socket:

| request | reply |
|---|---|
| `long_offset` exactly at the end | `bytes_after 0, value_len 0`, no error |
| `long_offset` one unit past it | **`BadValue`**, with `bad` = the long_offset |
| a type named and wrong | the ACTUAL type and format, `bytes_after = len(value)`, `value_len 0` — and checked BEFORE the offset |
| an absent name | `type None(0) format 0 nitems 0`, whatever the offset or type |
| `delete = 1` on a partial read | nothing deleted |
| `delete = 1` with `bytes_after == 0` | deleted, and the reply still carries the value |

`wmctrl`'s 1024-long ceiling on `_NET_CLIENT_LIST` is inherited exactly: `nitems 1024,
bytes_after 3904` for a 2000-entry list.

`ChangeProperty` on a shadow writes an **overlay**: shared by every client the way X shares
a property, beating the synthesized value for as long as the toplevel exists, and gone when
it closes. `xdotool set_window --name` writes `_NET_WM_NAME` and `WM_NAME` both as
`STRING` — that is xdotool's own bug, `_NET_WM_NAME` is a `UTF8_STRING` property in the
EWMH — and the proxy stores what it was given, so `xprop -id <shadow>` afterwards prints
`_NET_WM_NAME(STRING) = "recon-renamed"`, which is what the same command against a real X
server prints.

## The root

Synthesized on the root whether or not upstream has the name — sway deletes
`_NET_CLIENT_LIST` outright and never publishes the desktop pair:

| name | value |
|---|---|
| `_NET_CLIENT_LIST` | every window's id, real xid or shadow, in the backend's list order, bottom to top |
| `_NET_CLIENT_LIST_STACKING` | the same list |
| `_NET_ACTIVE_WINDOW` | the focused window's id, 0 for none |
| `_NET_NUMBER_OF_DESKTOPS` | `max(num_desktops(), get_desktop() + 1)` |
| `_NET_CURRENT_DESKTOP` | `max(get_desktop(), 0)` |
| `_NET_DESKTOP_NAMES` | from `workspaces()` where the backend has it; absent otherwise |
| `_NET_DESKTOP_GEOMETRY` | `[w, h]` of `display_size()`, which is where `wmctrl -d`'s `DG:` column comes from |
| `_NET_DESKTOP_VIEWPORT` | `[0, 0]` per desktop, one pair for each `_NET_NUMBER_OF_DESKTOPS`, which is where `wmctrl -d`'s `VP:` column comes from |
| `_NET_SUPPORTED` | EDIT: upstream's list first and unreordered, then every atom the proxy answers for that upstream did not name |

`_NET_SUPPORTING_WM_CHECK`, `_NET_SHOWING_DESKTOP`, `_NET_WORKAREA` and everything else on
the root PASS.

`_NET_SUPPORTED` is what turns four commands from exit 1 into exit 0. `xdotool get_desktop`,
`set_desktop`, `get_num_desktops` and `wmctrl -d` exited **1** on sway with *Your
windowmanager claims not to support `_NET_CURRENT_DESKTOP`*; through the proxy all four exit
**0**. What turned them is not the two properties but the list: each reads `_NET_SUPPORTED`
first and gives up before sending the read it came for — the capture of `xdotool
get_desktop` ends there, 36 requests in. The proxy's own list (`policy.SUPPORTED`) is **42**
names: the eight root names above, the six per-window names, the three client-message types
the proxy routes, the fourteen `_NET_WM_WINDOW_TYPE_*` atoms and the eleven `_NET_WM_STATE_*`
ones. Upstream's list comes first and unreordered — it is upstream's answer and the proxy is
adding to it — and only the names upstream did not already have are appended, which on
wlroots' 19 was **26** of them.

`wmctrl -d` through the proxy prints `0  * DG: 1280x720  VP: 0,0  WA: N/A  1`. The `WA:`
column is the one place it and `wwmctl -d` still disagree — see the table at the end.

### Freshness

The registry re-reads the compositor when its last read is older than **20 ms**, or when the
event pump has invalidated it. A `search` walk of five windows is served from one list, and
`list()` costs 0.08 ms on sway.

## Events

The proxy's event pump is one daemon thread and one byte on a pipe, because every `events()`
in this tree is a blocking generator and none of them is a selectable descriptor. It runs
only while some client holds a non-zero event mask on the root or on a native window, and
stops with the last one. A proxy nobody is watching through costs the compositor no sway
subscription, no Hyprland `socket2` connection and no loaded KWin script; the read side
stays fresh on the registry's own 20 ms TTL instead.

The three rows that used to be a timeout and now are not:

| command | before | now |
|---|---|---|
| `xprop -spy -id <shadow> WM_NAME` | 16 requests, then a block on the socket; RC 124 under a timeout, on Xvfb+openbox and on Xwayland+sway alike | prints the new title when the compositor retitles the window. Measured on headless sway, five runs: **0 to 20 ms** after sway itself reports the rename, against sway's own +17.5 ms for the `title` event. 20 ms is the reader's poll granularity, so the true figure is under it |
| `xprop -spy -root _NET_ACTIVE_WINDOW` | 14 requests, RC 124 | prints one line per `swaymsg focus`. **One** line: upstream's own root `PropertyNotify` for a name the proxy overrides is dropped on the way down, because the compositor is the single source |
| `xdotool behave <shadow> mouse-enter <cmd>` | 32 requests, RC 124 | runs the command when the pointer crosses into the window's rect. The chained command is an xdotool command, so it is `exec echo hit` and not `echo hit` — `echo` alone answers *Command failed.*, which is xdotool's own behaviour |

**Over-delivery is deliberate.** A `PropertyNotify` for an atom `xprop` is not watching
costs the client zero requests: it is filtered client-side, and four `PropertyNotify`s
arrived per rename during the survey while only the `WM_NAME` one drew a `GetProperty`. So
where one compositor field maps onto more than one property name — a workspace move
publishes `_NET_WM_DESKTOP` *and* `_NET_WM_STATE` — both go out, and a watcher that wants
fewer filters them itself, exactly as it does on X. What the proxy does not do is send a
second copy of somebody else's event: a real X window's per-window events are Xwayland's own
and pass untouched.

**A write arms a re-read.** A write the proxy consumes — `ConfigureWindow`, `MapWindow`,
`UnmapWindow`, `SetInputFocus`, `DestroyWindow`, `KillClient` and the routed EWMH
`ClientMessage`s — arms a re-read of the compositor at **+50 ms** and **+250 ms**. sway
sends no event at all for a floating `move position`, so the `ConfigureNotify` a watcher is
owed after `xdotool windowmove` comes from the difference between two listings and not from
the compositor. The numbers are the measurement: on headless sway 1.11 the new rect was in
`get_tree` on the first 5 ms poll of all ten runs — 0.9 to 3.6 ms after the IPC call
returned, 1.6 to 6.1 ms end to end — so the first poll is fourteen times the measured worst
case and the second is the backstop for a compositor an order of magnitude slower. Ten
floating `move position`s produced **zero** window events on a subscribed sway `events()`,
which is why the poll pair exists at all.

**The wlr floor and COSMIC are polled.** `zwlr_foreign_toplevel_manager_v1` and
`ext_foreign_toplevel_list_v1` + `zcosmic_toplevel_info_v1` have no `events()` at all, so
the proxy polls `list()` every **250 ms** there — Cinnamon's own rate for the same job. A
change is seen within a quarter second instead of within milliseconds; nothing else
differs, because the token is a hint and the diff is the truth either way. A stream that
dies is logged, waited out for 2 s, and rebuilt after a re-detect.

**The sequence an event carries** is the receiving client's own number — two clients
watching the same window get the same change with different sequences — but not simply its
request count. It is the count held back behind any reply that client is still owed: one
below the oldest sequence with a placeholder outstanding or a reply on hold, and the plain
count when there is neither. The reason is libxcb's reader again: an event stamped above a
reply that has not gone out marks that request completed with no reply, and the reply
arriving afterwards with a lower 16-bit sequence is widened by 65536 and the connection
tears down. Measured here as a bug in this very file: a client that pipelined `GetProperty`
and `NoOperation` got `PropertyNotify` seq 4, `PropertyNotify` seq 4, then the reply for
seq 3. `xprop -spy` never notices, because it pipelines nothing; an xcb status bar does.

Byte 31 of `EnterNotify` and `LeaveNotify` is a bitmask and not a flag: bit 1 is
`same-screen`, always set because this proxy has one screen, and bit 0 is `focus`, set when
the window the event names is the focused one. A plain `1` there would tell an Xlib client
the crossing happened on another screen.

## XTEST and the pointer

A `FakeInput` KeyPress or KeyRelease goes to **Xwayland, untouched**, when the compositor's
focused toplevel is an X window, and to the **input daemon** when it is a native one. That
is not a preference, it is the measured baseline:

* real xdotool through Xwayland types `ünï €ur ß λ 日` into an `xterm -u8` byte for byte,
  because it plants each keysym into a spare keycode of *Xwayland's own* map — a map no
  compositor reads and no seat has;
* routed to the input daemon instead, the same command wrote `n ur   ` and the daemon said
  `Can't type character 'ü' (not on the US layout). Skipping.` six times;
* Xwayland's own XTEST puts nothing at all into a focused `foot`, which is the case the
  daemon exists for.

Buttons and motion never ask that question and always go to the daemon: a click has to move
the **seat's** pointer, because that is what raises and focuses a window and what Xwayland
then sees. Xwayland's own warp moves only Xwayland's pointer — measured, a raw `WarpPointer`
to (321, 123) straight at Xwayland moved its `QueryPointer` there and the compositor's
cursor not at all, while `xdotool getmouselocation` on that display happily printed
`x:321 y:123`. "Nobody knows" — no registry, nothing focused — answers "Xwayland", because
that is the behaviour that works today.

A KeyPress whose keysym is a character the daemon reports unreachable on the active layout
is sent as one `type` of that character instead, and its release is consumed, because a
`type` is a press and a release already.

Every key and button a client is holding is released when that client disconnects, so a
killed `xdotool keydown ctrl` cannot leave Control down on the seat for ever. Two things
that release rests on, both measured: it goes to the half the **press** went to, not to
whatever has the focus when it arrives; and the daemon connection is not let go while
anything is held, because the 60-second linger timer counts from the last operation and a
held key sends none.

### Where the pointer position comes from, in order

1. **`backend.pointer()`**, the compositor's own cursor. Five backends answer it: GNOME
   (the bridge's `GetPointer`), KWin (`workspace.cursorPos`), Hyprland (`hyprctl j/cursorpos`),
   Wayfire (`window-rules/get_cursor_position`) and Cinnamon (`global.get_pointer()`).
   `xw11/server.py` calls it unconditionally, so on those five a hand on the mouse is seen. The
   base backend answers `None`, which is sway/i3, the wlroots floor and COSMIC: their IPC carries
   no cursor at all.
2. **The proxy's own last routed position** — every `FakeInput` absolute motion and every
   `WarpPointer` it sent to the daemon. This is what makes `getmouselocation` after
   `mousemove` answer the number the move asked for on sway, whose IPC carries no cursor at
   all.
3. **Xwayland's own answer.** On a `QueryPointer` that went upstream — which is every one
   `getmouselocation` sends, because it asks about the root — it is the reply's own number,
   untouched, and `child` is the only field the proxy replaces. On a `QueryPointer` aimed at
   a shadow there is no such reply, so the proxy asks its own connection: one round trip of
   about 70 µs, paid only there. On the headless rig the answer is `x:640 y:360`, the middle
   of the screen, because nothing has moved it.

With not one of the three answering, a `QueryPointer` on a shadow answers the window's own
origin and says so once in the log rather than once per request.

`child` in a reply the proxy answers for a shadow is always 0. X's `child` is the child of
the window asked about that contains the pointer, and a shadow has no children. On the
**root**, where `child` really is a child of the window asked about, it is the shadow under
the pointer — which is what makes `getmouselocation` print a `window:` the other clones
agree with.

Whatever answers is seeded into the daemon, once per position, so a relative move starts
from the truth rather than from the daemon's own last injection.

### Numbers, and bugs kept

A cold daemon spawn-and-connect is 52.3 ms and a warm round trip 0.243 ms; the proxy holds
the connection for 60 s after the last injection and retries a refusal after 5 s.
`xdotool key ctrl+a` puts **seven** `FakeInput`s on the wire and the daemon sees **four**
operations; the daemon dedupes nothing, so `key Control_L down` twice writes
`EV_KEY 29 value 1` twice to the uinput node.

* **`Warning: XTEST extension unavailable on '(null)'`.** With XTEST absent xdotool prints
  that literal `'(null)'`, sends no input request at all and exits 0 for `key`/`type`, 1 for
  `click`, 0 for `mousemove`. The proxy never produces it: it keeps upstream's `present=1`.
  The 28-request prologue that shape sends is kept as a fixture so the difference is
  readable — it loses three requests, not one, and still asks for 14 atom names.
* **`xdotool type` with `LC_CTYPE=POSIX` and non-ASCII input** aborts with *Invalid
  multi-byte sequence encountered*, exit 0, zero requests. Unchanged: nothing reaches the
  proxy.
* **The first character of the first `type` after a fresh focus.** Seen lost once during
  recon and never bisected. Measured again through this proxy: the first-ever type into a
  freshly created xterm wrote `armup` for `warmup`; ten types after ten fresh focuses wrote
  all ten byte for byte, into a `foot` and into an `xterm` alike, twice over. It is a
  first-USE race, not a per-focus one, and the proxy neither causes nor fixes it.
* **The remap path is racy at speed, with and without the proxy.** `ünï €ur ß λ 日` at
  `--delay 60` into a UTF-8 xterm, six direct runs interleaved with six proxied ones: whole
  3/6 direct and 2/6 proxied, one character lost each other time; under the load of a whole
  live-test run, two of the six lost once in four runs. So the envelope is four to six of
  the six and it widens with load. It is the xterm's own keymap cache against the
  `MappingNotify` pair xdotool sends around every character, and the proxy is in neither
  half of that exchange.

## RandR

The read side passes untouched, so `xrandr -q` through the proxy is byte-identical to
`xrandr -q` without one — pinned by a live test. The write side is collected inside the
client's own `GrabServer`, translated once, and applied as one layout when the grab closes.

| command | without the proxy | through it |
|---|---|---|
| `xrandr --output <o> --mode WxH` | `BadMatch` at `RRSetScreenSize`, **exit 1** | exit 0, and the compositor's output really changes |
| `--pos`, `--auto` | exit 0 and nothing happened | exit 0 and the output moves |
| `--primary` | exit 0; Xwayland keeps the flag and `-q` reads it back | exit 0, **and the compositor's own primary moves** on the two backends that have one: Mutter is sent `ApplyMonitorsConfig` with the primary flag on that connector's logical monitor, KWin `set_priority(dev, 1..N)` with the named output first. Measured on KWin 6.5 (resolute-kde, 2026-09-11): `xrandr --output Virtual-2 --primary` then `wxrandr --query` prints `Virtual-2 primary`, where it printed `Virtual-1` before. `--nograb` is the same. On sway, the wlr floor and Hyprland the flag is Xwayland's own and `wxrandr`'s `State` keeps the name, so the two planes agree but no compositor is told — see the table at the end |
| `--off` | `BadMatch`, exit 1, and the grab is leaked | exit 0, the output is switched off |
| `--rotate left` | `BadMatch`, exit 1, xrandr dies inside Xlib's handler with the server still grabbed | exit 0; sway's transform is `270` and the rect turns |
| `--scale NxN` | `BadValue` at `RRSetCrtcTransform`, exit 1 | exit 0 for a pure scale, and the client is left with the desktop X gives it: `--scale 2x2` on a 1280x720 head leaves `xrandr -q` printing `HEADLESS-1 connected 2560x1440+0+0` |
| `--newmode` + `--addmode` + `--mode <name>` | the first two worked; the third died | all three exit 0; the custom mode resolves to a real one of the same size and rate |
| `-s WxH` (RandR 1.1) | changes Xwayland's own screen and nothing else | the compositor's output moves too, and the reply is answered only after it has |
| two heads, `--right-of` / `--left-of` | `BadMatch`, exit 1 | exit 0; both heads move in one apply |

One apply through the sway backend takes **1 to 44 ms** on this box, over eleven
invocations: 1-3 ms when nothing changes, 8-11 ms for a position, 32-44 ms for a mode or a
transform. Mutter's `ApplyMonitorsConfig` waits up to **5 s** for `MonitorsChanged`, which
is why the apply runs on a worker thread and only the applying client's reads are paused.
The snapshot the proxy reads at `GrabServer` is two round trips plus one per output and one
per crtc plus two, at about 70 µs each — under a millisecond on one head.

**A failed apply is an X error, not a silent success.** `BadMatch` with `bad` = the root
when the batch carried a `SetScreenSize` (the bytes today's Xwayland answers that request
with), else `BadValue` at the last `SetCrtcConfig`, and `BadValue` for a batch that was
nothing but a `--primary`. Xlib's default handler prints its five lines and the tool exits
1, so a script that checks `$?` sees what it always saw; the compositor's own sentence goes
to the proxy log. One printed number differs from what Xwayland would have printed: the
*Serial number of failed request* is the grab's **closing** request and not the
`SetScreenSize`'s, because by then the `SetCrtcConfig` after it has already been answered,
and a 16-bit sequence that goes backwards makes libxcb widen it by 65536 and tear the
connection down. Measured: with the `SetScreenSize`'s own sequence, `xrandr` printed
`X connection to :83 broken (explicit kill or server shutdown)` and the five lines never
appeared at all.

`xrandr -s` refuses in the reply and not with an error, because RandR 1.1 has no error on
that path: `SetScreenConfig` answers a status byte, and xrandr turns `3` into *Failed to
change the screen configuration!* and exit 1.

`SetScreenSize` is **recorded and never applied** — a Wayland layout has no framebuffer to
size. It is not discarded: it is what a failure is attributed to, and the layout box the
targets produce is compared against it. A mismatch is one log line and not a refusal,
because xrandr sizes the framebuffer from the same arithmetic and a compositor may round
differently.

`--gamma` and `--brightness` through the proxy are **Xwayland's**: `RRSetCrtcGamma` passes
and `wxrandr`'s own gamma side-store is not touched. `--set <property>` and the EDID reads
are Xwayland's too — it owns the RandR output properties. A layout applied through the proxy
is never persistent: `wxrandr --persistent` writes Mutter's `monitors.xml`, and the proxy
always applies temporarily, because a long-lived proxy would otherwise inherit one wrapper's
variable and hand it to every client for the rest of the session.

Multi-output, as measured: one `SetCrtcConfig` per crtc plus at most one `SetScreenSize`,
all inside one grab, committed as one apply — on a two-head headless sway for `--right-of`,
`--left-of`, and a single invocation carrying a mode change and a relation together.
`--right-of` and friends add nothing to the wire; they are client-side arithmetic that ends
in the `x` field.

## The wrapper rules

`xw11/wrap.py` decides, in order. The first five cost no process at all.

1. a **library caller** — `main([...])` with an explicit argv, which is the whole test
   suite — is never replaced;
2. **`W11_PASSTHROUGH=never`**, or **`W11_PROXY=never`** (per tool `WDOTOOL_PROXY`,
   `WWMCTL_PROXY`, `WXPROP_PROXY`, `WXRANDR_PROXY`) — our own code runs;
3. **the session is not Wayland** — on X11 the handover to the original has already happened
   one line above, and the proxy is never started, never spawned and never even imported;
   with no session at all the clone's own refusal is the better message;
4. **the argv carries a clone-only token** — an option or command of ours the original has
   never had (the table below) — our code runs, because that flag is what was asked for;
5. **no original is installed** — the clone runs, silently;
5b. **a help or version request that opens no display** — `xdotool --help`, `xdotool -v`,
   `wmctrl --version`, `xprop -help`, `xrandr --help`, and a bare `xdotool` or `wmctrl` —
   the original runs, as it does on X11, and no proxy is started: a usage string is not
   worth a process that outlives the command by fifteen minutes. A bare `xrandr` or `xprop`
   is **not** one of these: the first prints the screen configuration and the second waits
   for a click, so both go through the proxy;
6. **the proxy could not be started** — the clone runs, and says so under `XW11_DEBUG`.

Otherwise the process is replaced by the original with `DISPLAY=:N` and, where the proxy
appended a cookie, `XAUTHORITY` naming the file it appended to.

`W11_PROXY=always` turns 5 and 6 into exit 127 with the same wording the X11 handover uses:
a script that asks for the original's bytes gets them or an error, never a silently
different implementation.

### The clone-only tokens

| tool | tokens | why |
|---|---|---|
| `xdotool` | `--layout`, `--vkbd`, `keys` | ours; xdotool has neither option and no `keys` command |
| `wmctrl` | — | every byte the clone takes, wmctrl takes |
| `xprop` | — | the same |
| `xrandr` | `--backend`, `--backends`, `--print-backend`, `--persistent`, `--gnome-overlap-status`, `--gnome-overlap-allow`, `--gnome-overlap-forget`, `--unsafe-gnome-overlap`, `--unsafe-gnome-overlap-unmeasured` | ours; `--q1` and `--q12` are xrandr's own compatibility tokens and belong to the original |

The `xrandr` row is not a substring scan: the wrapper asks `wxrandr`'s own argv walker, so
an output *named* `--persistent` (`xrandr --output --persistent --off`) is a value and goes
to the original whole — the same answer the X11 handover already gives.

`W11_PROXY=always` overrides rule 4, but only for the tokens that **reach** the wrapper:
`--persistent`, the five `--*gnome-overlap*` flags, `--layout` and `--vkbd`, which the
original then rejects in its own words. `--backend`, `--backends`, `--print-backend` and
`wdotool keys` never reach it under any variable, and that is right rather than a gap: they
are answered by their own `main()` several screens above the wrapper's call, because they
describe our own code and the original has nothing to answer them with. A user who spells
`--backend sway` has named the backend.

Both `main()`s hand the wrapper the argv as the **user** wrote it, before their own leading
options are stripped for the X11 handover: `xdotool --layout xkb type a` must not reach the
original as `type a` with the layout silently gone.

| `xdotool getwindowname <that id>` | foot's title | the same one |

keeps that cheap, and the `xrandr` row is why it is a *narrow* rule.

## What differs

One row per thing X does that `xw11` does not do yet, in the shape AGENTS.md asks for: the
X behaviour, what `xw11` does, the route on AGENTS.md's ladder that would close it, and what
that route costs. A row with no route number is a choice with a cost rather than a gap, and
says so.

### The wire and the process

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| A client may declare MSB-first byte order (`'B'` at byte 0 of its setup) and the server byte-swaps every field for it. | Answers a `Failed` setup naming MSB-first clients as **not yet** and closes the connection. Nothing on any measured box has ever sent one: all ~20 connections captured during recon were `'l'`, and `x11_mini.py` has said "byte order 'l' only" since 0.1. | 5 | a byte swap on every field of every request and reply the proxy reads, on the hot path, for a client class nobody has produced |
| `QueryExtension("DRI3")` answers `present = 1` where the server has DRI3, and the client then receives GPU buffers as descriptors over the socket. | Answers `present = 0` on the way down — a one-byte, length-preserving edit, so no sequence moves. Everything else stays advertised, `XWAYLAND` included, and `ListExtensions` is untouched, so DRI3 still appears in `xdpyinfo`'s list. | 5 | until the proxy splits a descriptor off the byte stream with `sendmsg` at the right offset, a client told "present" would take a path that breaks with no error at all — so it is told the truth instead. No box in this project has a `/dev/dri` |
| Any descriptor a client or server passes over the X socket with `SCM_RIGHTS` arrives at the other end. | Reads with `recvmsg` and a 64-byte ancillary buffer, closes every descriptor that arrives and writes one line naming it. A plain `recv()` would take the payload and drop the descriptors silently — measured. | 5 | the same as the row above: forwarding one needs the offset in the stream it belongs to. Closing and logging is what keeps it from being invisible |
| A client that sends a zero 16-bit request length without BIG-REQUESTS gets `BadLength`; an *extension* request whose minor opcode that extension does not have gets `BadRequest` instead, because the server validates the minor first. | Answers `BadLength` in both cases, consuming four bytes and sending a `NoOperation` upstream so the sequence delta stays zero. Measured against Xvfb 21.1.22 and pinned as a fixture; the four bytes are measured too — a zero-length header followed by 16 bytes of body drew one `BadLength` and the next request came back as sequence 7. | 5 | telling the two apart needs every extension's minor-opcode table, which is a table per server generation; the request is malformed either way and nothing measured sends one |
| An X server lives as long as the session. | Exits 900 s after its last client leaves, checked every 15 — and also when the session's Wayland socket is gone, or when its own display file is unlinked. The next wrapped tool starts it again. | — (a choice) | a reopened upstream connection re-bases every shadow id, so an id saved across more than fifteen minutes of no X-tool use may name nothing. The route to permanent ids is a proxy that never idles (`programs.w11.proxy.enable`, or `xw11 --foreground` from an autostart) at the cost of Xwayland pinned for the session |
| The X server answers every client itself and one client's slow request never delays another's. | Backend calls are made on the loop thread under one lock, so a compositor that hangs delays every other client's request by at most that backend's own timeout, **10 s**. No byte is lost: the delayed client's requests sit in its out-buffer and are answered in order afterwards. | 5 | a worker thread per backend call costs a lock per registry entry instead of one per process, and an answer that can be written while an older one is still being computed. The measured costs are what make the single thread safe — `list()` 0.08 ms, `get_desktop()` 0.02 ms on sway, `detect()` 0.7 ms |
| Nothing: X has no equivalent. | On Cinnamon only, the compositor's event stream is stepped under the same lock the proxy's own calls take, because that backend diffs `list()` over the same `org.Cinnamon.Eval` bus from the pump's thread. The lock is held across the whole step, so a read from the loop waits for that backend's current 0.25 s diff. | 5 | one lock per bus call instead of one per step is not yet written; it costs a backend that knows about a lock the proxy owns. Two threads on one bus is two answers on one socket, which is the failure the coarse lock buys off |
| Every window on the display appears in the server's own tree. | Where there is no Wayland session at all — no compositor socket, no session bus, no toplevel protocol — the proxy serves in pass-through: every request forwarded byte for byte, and one log line saying the shadow side is off and why. `--passthrough` asks for the same thing on purpose. | — (the honest answer) | native toplevels are invisible in that mode, which is what they are without the proxy too. The route back is a session for detection to find; `WDOTOOL_BACKEND=` forces one where detection cannot |

### Window ids

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| A window id means the same window until that window is destroyed, however long the client waits between two invocations. | A shadow id is minted out of the proxy's own connection's range, and that connection is opened at the first client and held while any client is connected and for 900 s after the last one leaves — so an id means the same window across every pair of invocations less than fifteen minutes apart. An Xwayland restart, or a longer gap, re-bases every one of them. | — (a choice) | the route to ids that never move is a proxy that never idles, at the cost of Xwayland pinned alive for the whole session, which is a behaviour change of its own: today it dies fifteen seconds after its last client and sway relaunches it lazily |
| An X server reclaims a destroyed window's id and hands it out again. | Never reuses a shadow id while it lives. The range is 2^21 ids, which is **24 days at one window a second**, and the proxy idles out fifteen minutes after its last client, so no session that can exist reaches the end of it. The mint after the last id is `BadAlloc` on the request that needed it plus one log line, and it stays refused. | 5 | a free list with a grace period is the thing not yet written; its cost is an id that names two different windows inside one script's lifetime, which is exactly the bug the 24-day arithmetic says nobody can hit |
| A packet whose length field lies is a broken X server and libxcb drops the connection. | The proxy's own connection does the same and no more: it stops framing, the loop closes that socket, every client keeps its own connection, and the next client accept reopens the proxy's connection with the registry re-based. | — | the shadow ids minted from the old connection are gone, which is the same cost an Xwayland restart carries |

### Properties, geometry and the lists

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| `ListProperties` answers in the server's own order, which is creation order reversed — the live xterm on the rig answers thirteen names in that order. | A shadow has no creation order to reverse, so the proxy answers a fixed table order and pins it in a fixture. | — (the honest order for a window nobody created) | a consumer that depends on server order sees a different order for a shadow than for its X twin. Whether anything does is unmeasured |
| `WM_NORMAL_HINTS` carries min, max and increment sizes; `windowsize --usehints` and tiling scripts read it. | Not synthesized. `windowsize --usehints` on a shadow sizes in pixels, which is what `flags = 0` would also have done. | 3 on GNOME (the bridge already walks `MetaWindow`), 2 elsewhere | a per-backend size query on every property read, or a cache with the registry's 20 ms TTL |
| `WM_HINTS` carries the urgency bit, the input hint and an icon pixmap. | Not synthesized. The urgency bit is already `_NET_WM_STATE_DEMANDS_ATTENTION` where a backend reports it; the input hint and the icon pixmap have no source at all. | 6 for the input hint | a compositor patch per compositor, for a hint only a toolkit reads |
| `_NET_WM_ICON` carries the app icon; panels and `wmctrl -lx` consumers read it. | Not synthesized. | 3 on GNOME, 2 on KWin | one icon decode per window and kilobytes per property read. A `.desktop` lookup off the backend's `desktop_id` is a rung lower and lossy |
| `_NET_WM_USER_TIME` is the window's last user interaction, for focus-stealing prevention. | Not synthesized: no compositor publishes a per-window last-interaction timestamp. | 6 | a compositor patch per compositor |
| `_NET_WM_ALLOWED_ACTIONS` tells a pager which of the EWMH verbs will work. | Not synthesized. | 5 | it is derivable from what each backend refuses, which is a table of refusals per backend rather than a compositor fact — and a table that goes stale silently |
| `_NET_FRAME_EXTENTS` is the decoration thickness. | Four zeroes, which is the true number: the rect every backend reports is the whole toplevel and `GetGeometry` answers that same rect. | 2 | a per-backend frame geometry query (KWin's `frameGeometry` minus `clientGeometry`, sway's `deco_rect`), at the cost of one more IPC field per window and a number that is zero on every tiling compositor anyway |
| `GetGeometry` answers the window's real rectangle. | On the wlr floor (labwc, river, Budgie, Xfce-on-Wayland, LXQt-on-Wayland) an **XWayland** window answers the X server's own rectangle: `WlrBackend.list()` pairs the toplevel to `_NET_CLIENT_LIST` and takes the rect from there, so `getwindowgeometry` on an xterm reads `718,395 484x316` where it used to read `0,0 1920x1080` [M resolute-labwc golden 2026-09-12, against `xdotool getwindowgeometry 0x40000c` on the same session]. A **native** toplevel still answers `0, 0, out_w, out_h`: `zwlr_foreign_toplevel_management_v1` carries no rect and no X server has heard of the window, so the row is the one surviving geometry **not yet**. `wwmctl -lG` prints the same pair of answers, so the two tools agree. Two XWayland windows the join cannot tell apart — two xterms under the default title — both keep the floor: `match_xids` hands out no id on a tie, and the tie-break route 5 lacks is a rectangle on the Wayland side, the same rung-1 gap. | 1 for the native half | a foreign-toplevel protocol that carries a rect, which costs wlroots writing and shipping one — `ext-foreign-toplevel-*` has none either. Below that it is rung 6, a patched compositor with one geometry event per window, or rung 2, the compositor's own IPC, one backend at a time, which is why sway, Hyprland, Wayfire and COSMIC already report a true rect |
| `_NET_CLIENT_LIST_STACKING` is the bottom-to-top stacking order, and a pager raises by it. | A copy of `_NET_CLIENT_LIST`: sway's tree is not a stacking order and no backend in this tree reports one, so the two lists are the same list, and a test pins the copy rather than letting a wrong order slide past a client. | 2 per backend | KWin's `stackingOrder` is one property read; the sway tree would need a second walk. One more IPC call per re-list under a 20 ms TTL |
| `_NET_WM_STATE` carries eleven state bits. | On a `views()` backend — GNOME, Cinnamon, KWin, Hyprland, Wayfire, the wlr floor — all eleven. On sway and i3 only `FULLSCREEN` and `STICKY`, because the other nine need a field the tree node has not got. | 1 (sway's own IPC, which does not publish them today), else 6 | one more field in sway's tree node, or a compositor patch. `FOCUSED`, `MAXIMIZED_*`, `ABOVE`, `BELOW`, `SKIP_*` and `DEMANDS_ATTENTION` are the ones missing there |

### Writes

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| `xdotool set_window --name` renames the window every client sees, and a window manager's title bar with it. | Renames the X-visible property, which is what `set_window --name` means on X, and does not change the title the compositor's own bar, `swaymsg -t get_tree` or `wdotool getwindowname` shows. | 2, and **not yet** on every backend | none of the six has a per-window title verb today — sway and i3 have no `title` command, KWin's `caption` is read-only, Mutter's `MetaWindow` title is the client's — so the real cost is a compositor patch (rung 6) per compositor, for a rename only X clients would have read anyway |
| `wmctrl -k on` hides every window and shows the desktop. | Exits 0 and nothing happens. The `SendEvent` is forwarded to the X server, where wlroots' xwm ignores it too, and one log line says so. The atom is deliberately **not** in the proxy's `_NET_SUPPORTED` union, so a tool that gates on it is told "no", which is the honest answer until the verb exists. **Not yet.** | 2 for five of the six, 3 on GNOME | one `WindowBackend.show_desktop(bool)` plus one implementation per backend: sway/i3 `move scratchpad` and back, KWin's `Workspace.showingDesktop`, Hyprland's `togglespecialworkspace`, Wayfire's `showdesktop` plugin, Cinnamon's `Main.overview`, and the bridge extension on GNOME |
| A client creates a window with another client's window as its parent, or `ReparentWindow`s one — old-style taskbars, frame-drawing window managers, XEmbed panel applets. | `CreateWindow` and `ReparentWindow` pass, so naming a shadow draws Xwayland's own `BadWindow`: the shadow id is not an id that server ever minted. **Not yet.** Nothing in xdotool, wmctrl, xprop or xrandr sends either at a foreign window. | 5 | the proxy would have to create a real Xwayland window per shadow, keep it over the compositor's toplevel and forward geometry both ways — the "one X window per toplevel" design the shadow model exists to avoid. A second window per shadow, a `ConfigureNotify` loop between the two planes, and no way to keep the child above the toplevel's own content |
| `ConfigureWindow` stacks a window relative to a named sibling (`TopIf`, `BottomIf`, `Opposite`) and sets a client-owned border width. | `Above` and `Below` become `raise_` and `lower`; `border_width` and `sibling` are ignored with one log line each. A Wayland toplevel has no client-owned border and no sibling to stack against. **Not yet** for the three relative modes. Nothing in the four tools sends any of them. | 2 | the compositor's own stacking IPC, one verb per backend |
| A synthetic event sent to a window (`xdotool key --window <w>`, which is `SendEvent` of a `KeyPress`) is delivered to that window's selectors. | Forwarded, so a shadow draws Xwayland's `BadWindow`: the shadow is an id that server never minted. **Not yet.** | 5 | the machinery is the proxy's own event writer; the cost is deciding delivery for a window the X server does not know about |
| `ChangeProperty` with `Prepend` or `Append` whose type or format disagrees with the property's answers `BadMatch`. | Dropped with a log line. **Not yet.** Nothing measured sends one — `xprop -set` and `xdotool set_window --name` are both `Replace`. | 5 | the seam is ours: the request handler can consume a request or answer it, not both. One class in `xw11/policy.py` and its arm in that method |

### Events and input

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| `EnterNotify`, `LeaveNotify` and `MotionNotify` follow the real pointer, whatever moved it. | They follow it on GNOME, KWin, Hyprland, Wayfire and Cinnamon, whose compositors answer for their own cursor. On sway/i3, the wlroots floor and COSMIC the IPC has no cursor in it, so a hand on the mouse is not seen and the proxy says so once per session in its log rather than inventing a position. **Not yet** there. | 4 | evdev — the same `/dev/input/event*` the input daemon already opens for uinput. The grant it needs is a `SUBSYSTEM=="input", KERNEL=="event*", TAG+="uaccess"` line in `gnome/60-w11-uinput.rules`, and we decline it: it hands the active-seat user read *and write* on every input device, a standing keylogger channel that follows a VT switch to the next seated user, which is the same objection that file's own comment already makes to `GROUP="input"`. Until a route with a smaller grant exists, this row stays. |
| `xdotool selectwindow` grabs the pointer on the root and waits for a `ButtonRelease` anywhere. | The grab passes to Xwayland and the release it waits for is Xwayland's: a click on an X window arrives, a click on a **native** window arrives at the compositor and never at Xwayland. **Not yet.** | 1 | a layer-shell surface that takes the press, which the proxy has to create and place on every compositor that speaks `wlr-layer-shell`. `backend.select_window()` is the clone's picker and is not what the client asked for: it asked for a grab |
| The compositor pushes every toplevel change. | On the wlr floor and COSMIC there is no event stream at all, so the proxy polls `list()` every 250 ms. A change is seen within a quarter second instead of within milliseconds. **Not yet** for a pushed stream. | 1 | the handlers are already there and already fire on every title, app_id, state and closed, and the connection is a plain socket — the cost is teaching the pump to `select()` on it between dispatches, which nothing in this tree has tested yet |
| A character outside the compositor's layout is typed by remapping a spare keycode. | Every character the keymap `wdotool` uploads binds — all of ASCII, plus `€` (evdev 435) and `±` (118) — resolves to a keycode instead of being skipped, and it types on **both** sinks. On the **virtual-keyboard sink**: `wdotool --vkbd on type -- '€X'` lands `b'\xe2\x82\xacX'` in a focused `foot` on headless sway 1.11 (measured 2026-09-11). On the **kernel sink** (`--vkbd auto` wherever /dev/uinput is usable) `uinput.keyboard()` registers the `keymap.UPLOADED_EXTRA_KEYS` codes on top of keybits 1..255 (`wdotool/uinput.py:169`), so evdev 435 is no longer dropped and `€` arrives — measured by the euro batch 2026-09-11: without that registration `wdotool type €` through /dev/uinput on a plain `us` session typed nothing, with it the three UTF-8 bytes land. The cause was never the compositor's layout: `key <I443> { [ 0x20ac ] }` was in `wdotool/us_keymap.py` all along and `wdotool/keymap.py` stopped at ASCII. Into an X window it is Xwayland's own remap, unchanged. A character the uploaded keymap binds **nowhere** is still skipped, with the character and the layout named — **not yet** — and X does it too. | 1 | The one remaining not-yet is a character the uploaded map binds nowhere: `zwp_virtual_keyboard_v1.keymap` takes any map, so the daemon can put the wanted keysym on a spare keycode in a copy of the one it uploads and press that (route 1) — at the cost of a re-upload and a re-press mid-`type`, which swaps the keymap under the focused client between two keystrokes and is unmeasured on every compositor |
| `QueryPointer`'s `mask` carries the modifiers the user is physically holding. | On a shadow, only what this proxy is holding. **Not yet.** | 4 | evdev again, and the same `/dev/input` read access |
| An XKB latch a client sets lands on the one keyboard state there is. | Lands on Xwayland's XKB state, which the compositor never sees. **Not yet.** | 4 | a latch model in the daemon beside its held-key one |
| `xdotool keydown ctrl` holds Control across the next commands until something releases it. | Into a native toplevel, the key is released when that command's client exits, so the `xdotool click 1` behind it is unmodified. Into an X window it is X's own behaviour, unchanged. **Not yet** for the native half. | 2/3 | the daemon's own held-key state already outlives a client, so the proxy can leave a key held on disconnect and let the seat end exactly where X leaves it — at the cost of a killed `keydown` leaving Control down until the next `keyup` or the daemon's own idle exit, which is precisely what X does. A `W11_XTEST_RELEASE_ON_CLOSE` flag the original never had would keep today's safer behaviour |
| `FakeInput` types into whatever has the focus. | With no route to the input daemon at all it goes to Xwayland: X windows type, native ones get nothing. The log carries the sentence and the rung. **Not yet.** | 4, or 1 | `/dev/uinput` with the udev rule that grants the seat user access, or `zwp_virtual_keyboard_v1` where the compositor speaks it |

### The work area

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| `_NET_WORKAREA` is the usable screen rectangle minus panels and struts, and `wmctrl -d` prints it in the `WA:` column. | The proxy PASSes `_NET_WORKAREA` to the compositor, and sway (and the wlr floor) publishes none, so `wmctrl -d` through the proxy prints `WA: N/A` — the byte the X server hands back — where `wwmctl -d` reads the backend's own work area and prints it. This is the one place `wmctrl -d` through the proxy and `wwmctl -d` still disagree. **Not yet** for a synthesized `_NET_WORKAREA`. | 2 | the backend's work-area query is already what `wwmctl -d` reads, so the proxy can answer `_NET_WORKAREA` out of it rather than PASSing — at the cost of one root property per desktop, and a struts-vs-whole-output choice that is the compositor's to make, not X's |

### RandR

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
| Each write in a grab is applied as it arrives, so a client that dies mid-batch leaves the writes it managed to send. | A batch the client abandons is dropped, not applied — `xrandr` dies inside Xlib's default error handler mid-write on today's Xwayland with the server still grabbed and its `UngrabServer` never sent, and what it collected by then is half a layout: a disable with no enable. One log line says it happened. | — (a choice) | applying half a layout turns a screen off with nothing left to turn it back on |
| An output the server switches off stays listed with no crtc, and `--auto` brings it back. | After `xrandr --output HEADLESS-1 --off`, Xwayland stops listing it at all, so `xrandr --output HEADLESS-1 --auto` prints `warning: output HEADLESS-1 not found; ignoring` and exits 0 with nothing done. **Not yet.** `wxrandr --output HEADLESS-1 --auto` turns it back on today, because it asks the compositor and not the X server. | 1 | `zwlr_output_management_v1` lists disabled heads, so the proxy can put the missing outputs back into the `GetScreenResources` and `GetOutputInfo` replies — at the cost of a read-side edit the design does not have, and of minting RandR ids of its own for them |
| A mode list is the monitor's, and a mode that was there before a resize is there after it. | A headless output's mode list follows its size: at 1280x720 Xwayland lists sixteen modes down to 640x350, and after the compositor moves the head to 800x600 it lists ten, none larger — so `xrandr --output HEADLESS-1 --mode 1280x720` then answers `cannot find mode 1280x720` client-side, before a byte goes out. On a monitor with an EDID the list does not move. **Not yet.** `wxrandr` does it today, because it never asks the X server what the output can do. | 1 | the same read-side edit as the row above: the compositor's output management knows the sizes a virtual head takes, at the cost of `xrandr -q` through the proxy no longer being byte-identical to `xrandr -q` without one |
| A mode `xrandr -q` lists for an output is a mode that output can be set to. | Not on a virtual head: Xwayland fabricates a CVT ladder off the head's current logical size and the compositor's list is the EDID's, and the two need not overlap at all. Measured on the rig on 2026-09-11, two QEMU virtual heads under sway 1.11: `xrandr -q` offered 1920x1080, 1440x1080, 1400x1050, 1280x1024 and twenty more, sway offered 1920x1080, 5120x2160, 3840x2160, 1920x1440, 2560x1080 and the rest of the EDID's — one entry in common, the current mode. So `xrandr --output Virtual-2 --mode 1440x1080` through the proxy is `BadMatch` at `RRSetScreenSize`, exit 1, with `cannot find mode 1440x1080` in the proxy log: the compositor refusing a mode it has not got. `--pos` and `--off` on the same head are exit 0 and really move it. **Not yet.** | 1 | the same read-side edit as the two rows above: `zwlr_output_management_v1` carries the modes a head really takes, so the proxy can answer `GetScreenResources` and `GetOutputInfo` out of the compositor rather than passing Xwayland's — at the cost of `xrandr -q` through the proxy no longer being byte-identical to `xrandr -q` without one, which is the property a live test pins today |
| `--fb WxH` alone grows the framebuffer past the outputs and the pointer pans around it. | Exits 0 and moves nothing — the 0 X gave it, rather than an error X never wrote. The log carries the route. A `--fb` that comes **with** a crtc change, which is every `--mode`, `--rotate` and `--scale`, is applied as that change and the size compared against the layout. **Not yet.** | 1 | a scale below 1 on the head gives a bigger rect (measured: `scale 0.5` gives 2560x1440), at the cost of scaling the outputs rather than leaving a bigger screen behind them. A framebuffer genuinely larger than every output, with panning, is rung 6 |
| `--transform` takes any 3x3 matrix, shears and translations included. | A pure scale is applied; anything else answers `BadValue`. **Not yet.** Today's Xwayland answers `BadValue` for *every* transform including the pure scale, so the bytes a client sees for the refused ones do not change. | 6 | no output-management protocol carries such a matrix, so it is a compositor patch, shipped and maintained per compositor |
| `--panning` sets a panning viewport on a crtc. | Passes to Xwayland and does nothing. **Not yet.** | 6 | no output-management protocol has a panning viewport either |
| A custom modeline is a modeline, and the server drives it. | A `--newmode` mode is refused when no real mode of its size is within 1.0 Hz of it: a compositor is handed a mode or a size, never a modeline. A virtual head is the exception the CLI already makes — a headless output reports no modes and takes whatever size it is given, so the three-step `--newmode`/`--addmode`/`--mode` applies there. | — | where a real mode list exists and nothing in it matches, the refusal is the X error above, and `wxrandr` refuses the same layout in its own words |
| `--scale 2x2` makes the crtc read a 2560x1440 rectangle through a 1280x720 mode: the screen grows and everything on it shrinks. | The same, as X does it: the proxy hands the compositor the reciprocal, because a Wayland output's `scale` runs the other way (`scale 2` gives a 640x360 rect, `scale 0.5` a 2560x1440 one — measured). `wxrandr --scale 2` keeps the compositor's meaning, so the two front ends disagree by a reciprocal on purpose: one is xrandr's flag, the other is `wxrandr`'s. | — | `--scale 1x1` afterwards does not put a headless head back: it exits 0 and the compositor's scale really returns to 1.0, but by then the crtc's current mode *is* 2560x1440, which is the mode xrandr re-sends. Same cause as the mode-list row, same route |
| `SetCrtcConfig`'s reply carries a fresh `config_timestamp` minted by the server. | Echoes the request's own. Nothing xrandr does reads it back, and the proxy has no clock of the server's to mint one from. | — | a client that diffs timestamps across two applies sees no change |
| A layout can be saved. | An apply through the proxy is never persistent. | — (a choice) | a long-lived proxy would otherwise inherit one wrapper's `WXRANDR_PERSIST` and hand it to every client for the rest of the session. `wxrandr --persistent` stays the front end for it |
| A layout whose monitors overlap is the client's business. | On Mutter it is refused by the same check `wxrandr` runs, the refusal reaches the client as the X error above, and the log names `--unsafe-gnome-overlap` as the flag that would allow it. | — | there is no RandR question to ask a user mid-grab; the consent flow is `wxrandr`'s |
| Multi-output batches on Mutter and KWin. | Applied as recorded. Measured on a two-head headless sway, and on the `proxy` phase of every KDE and GNOME flavor of CI run 34628777544 (13 then) — `--pos` through the proxy moves the compositor's own output there, and R9 (the original xdotool typing into a native window) passed on all 13. | — | — |
| The primary output is the compositor's, and `xrandr --output X --primary` moves it. | It does, on the two backends that have a primary of their own: Mutter's `ApplyMonitorsConfig` primary flag and KWin's `set_priority`. Measured on KWin 6.5 (resolute-kde, 2026-09-11): read back as `Virtual-2`, grabbed and `--nograb` alike, where every GNOME/KDE flavor read back `Virtual-1` before. On sway, the wlr floor and Hyprland the request PASSes to Xwayland — which keeps the flag and answers `xrandr -q` with it — and `wxrandr`'s own `State` keeps the same name, so the two planes agree, but no compositor is told. **Not yet** there. | 1 | a foreign primary verb: `zwlr_output_management_v1` has no primary at all and `kde_output_order_v1` is KWin's own, so the route is a protocol that carries one (on sway it is rung 6, `swaymsg` has no primary either). Cost: an upstream protocol addition, which is why the X-visible half is served out of Xwayland today |

### Sessions the proxy cannot reach

| X behaviour | what xw11 does | route | cost |
|---|---|---|---|
